# Use-cases и их workflow

Это черновик. Данный файл нужен для собственного понимания требований к функционалу.

## 1. Получение тестового токена (dummyLogin)

1. Пользователь отправляет POST /dummyLogin с указанием роли (admin или user)
2. Система возвращает JWT-токен, в котором зашиты фиксированный UUID пользователя и его роль
3. Этот токен нужно передавать в заголовке Authorization Bearer во всех последующих запросах

## 2. Создание переговорки (только admin)

1. Администратор получает токен через /dummyLogin с ролью admin
2. Администратор отправляет POST /rooms/create с именем переговорки (и опционально: описание, вместимость)
3. Система создаёт переговорку, присваивает ей UUID и возвращает объект переговорки
4. На этом этапе переговорка существует, но **без расписания** — бронировать её пока нельзя

## 3. Создание расписания переговорки (только admin, только один раз)

1. Администратор отправляет POST /rooms/{roomId}/schedule/create
2. В теле запроса указываются: дни недели (например, 1,2,3,4,5 — пн-пт), время начала и конца рабочего окна (например, 09:00–18:00)
3. Система сохраняет расписание и на его основе умеет генерировать слоты по 30 минут (09:00–09:30, 09:30–10:00, ..., 17:30–18:00)
4. Если расписание для этой переговорки уже создано — система возвращает 409, изменить его нельзя
5. Если переговорка не найдена — 404

## 4. Просмотр списка переговорок (admin и user)

1. Авторизованный пользователь (любая роль) отправляет GET /rooms/list
2. Система возвращает все переговорки — неважно, есть у них расписание или нет

## 5. Просмотр доступных слотов (admin и user)

1. Авторизованный пользователь отправляет GET /rooms/{roomId}/slots/list?date=2024-06-10
2. Система проверяет, существует ли переговорка — если нет, возвращает 404
3. Система проверяет, есть ли у переговорки расписание — если нет, возвращает пустой список
4. Система проверяет, входит ли указанная дата в рабочие дни по расписанию — если нет (например, воскресенье при расписании пн-пт), возвращает пустой список
5. Система генерирует все слоты на эту дату по расписанию (например, 17 слотов по 30 минут)
6. Система фильтрует слоты: убирает те, на которые уже есть **активная** бронь
7. Возвращается список свободных слотов с их UUID, временем начала и конца

## 6. Создание брони (только user)

1. Пользователь получает токен через /dummyLogin с ролью user
2. Пользователь смотрит доступные слоты (use-case 5) и выбирает нужный slotId
3. Пользователь отправляет POST /bookings/create с указанием slotId (и опционально: createConferenceLink: true)
4. Система проверяет роль — admin не может бронировать, возвращает 403
5. Система проверяет, существует ли слот — если нет, 404
6. Система проверяет, что слот не в прошлом — если start < now, возвращает 400
7. Система проверяет, что слот не занят другой активной бронью — если занят, 409
8. Система создаёт бронь со статусом active, userId берётся из JWT (не из тела запроса)
9. Если был флаг createConferenceLink: true — система обращается к внешнему сервису и сохраняет ссылку на конференцию в брони
10. Система возвращает созданную бронь

## 7. Просмотр своих броней (только user)

1. Пользователь отправляет GET /bookings/my
2. Система берёт userId из JWT-токена
3. Система возвращает только те брони этого пользователя, у которых **слот в будущем** (start >= now)
4. Прошедшие брони в ответ не включаются

## 8. Отмена брони (только user, только своя)

1. Пользователь отправляет POST /bookings/{bookingId}/cancel
2. Система проверяет роль — только user может отменять, иначе 403
3. Система ищет бронь по bookingId — если не найдена, 404
4. Система проверяет, что бронь принадлежит текущему пользователю (userId из JWT) — если чужая, 403
5. Если бронь уже отменена (статус cancelled) — система всё равно возвращает 200 с текущим состоянием (идемпотентность)
6. Если бронь активна — система меняет статус на cancelled, слот снова становится свободным
7. Система возвращает актуальное состояние брони

## 9. Просмотр всех броней с пагинацией (только admin)

1. Администратор отправляет GET /bookings/list (опционально: ?page=1&pageSize=20)
2. Система проверяет роль — только admin, иначе 403
3. Система возвращает постраничный список всех броней всех пользователей
4. В ответе также возвращается объект pagination с текущей страницей, размером и общим количеством записей

## 10. Health-check (/\_info)

1. Любой запрос на GET /\_info
2. Система возвращает 200 OK — используется для проверки, что сервис живой
